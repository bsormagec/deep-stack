This morning's post was about a model getting bigger. GLM-5.4 is a 750-billion-parameter loop transformer that its makers compare to models two to four times its size. This afternoon's story runs the other direction, and it is the more useful one for anyone who actually runs models. Nari Labs, a small team led by Doyeob Kim, has shipped a 27-billion-parameter agent model in a 10-gigabyte file that matches — and on two benchmarks beats — the full-precision original. The interesting thing about NariQ is not that the file got smaller. Files get smaller every month. The interesting thing is which part of the model survived the squeeze: the long, messy, hundred-thousand-token agent sessions where every previous sub-3-bit quantization fell apart.

## The part that used to break

Quantization has always had a calibration problem, and the paper states it plainly. Most low-bit methods are calibrated on short web text and judged on perplexity, a single-number guess at how surprised the model is by the next token. That works fine for short answers. It fails for agents. An agent session is not a short answer. It is tool calls over many steps at contexts of 100,000 tokens or more, with the model reading its own earlier reasoning, checking tool output, and correcting itself. The paper's own numbers show how badly the old approach did there: existing quantizations of Qwen3.8-27B at or below 3 bits per weight match full precision on short tasks like AIME, yet in published results solve at most 72% as many tasks as the full-precision model on DeepSWE, a long-horizon agentic benchmark. Nearly a third of the agent's work simply vanished in the compression.

That sounds like a rounding problem. It isn't. It is the difference between a model that finishes a job and one that wanders off halfway through it and bills you for the wandering. A coding agent that solves 72% as many tasks as the original is not a cheaper version of the original. It is a different, worse tool that happens to share a name.

NariQ's bet is that the calibration data was the problem, not the bit budget. Instead of calibrating on web text, the method calibrates on tokens the full-precision model itself generated inside agent sessions — the actual distribution of long-horizon work, including the long reasoning traces and the tool-call loops. The quantization itself is trellis-coded: vectors of weights are quantized jointly through a trellis lookup, building on QTIP, a 2024 method from Tseng and colleagues, rather than rounding each weight independently. The result is stored in a custom tensor layout that runs on a single GPU.

## What the numbers actually say

The files shipped November 20, 2026, as GGUFs on Hugging Face, with the technical report on arXiv two days earlier. The base model is Qwen3.8-27B, a dense 27-billion-parameter model with a native 262,144-token context, released under Apache 2.0. In full BF16 precision it occupies 53.8 GB. NariQ's 3-bit file is 10.12 GB. The 2.5-bit file is 8.44 GB. The 2-bit file is 6.75 GB. Roughly a fivefold shrink at the default setting, from a file that needs a datacenter card to one that fits on a 24 GB consumer GPU with room for context.

The benchmark table on the model card is where the claim lives or dies. The agent runs were driven by the Claude Code CLI, version 2.1.309, with thinking on and a 262,144-token context — the same harness for every row. On DeepSWE v1.1, 113 tasks run three times each, the full-precision model solved a mean of 45.0 tasks, or 39.8%. The 3-bit file solved 46.3. The 2.5-bit file solved 47.3 — the best score in the table. The 2-bit file solved 32.3, and the card itself says to use the 2.5-bit or 3-bit file instead. On Terminal-Bench 2.1, 82 tasks times three attempts, full precision scored 62.6; the 3-bit file scored 63.8; the 2.5-bit file scored 60.2. On AIME, the short math test where old quants already did fine, the 3-bit file scored 98.3 against 97.7 for full precision. On multilingual math (MGSM) it gave back a little, 93.1 against 94.0, and on image understanding (RealWorldQA) it tied, 82.4 against 82.4.

Two things matter here beyond the headline. First, the 3-bit file does not merely match full precision on the agent benchmarks. It scores slightly higher on both of them. That is almost certainly noise — a point or two across three rounds of 113 tasks is well within run-to-run variation, and the paper's own framing is "stays level with," not "beats." Anyone presenting this as a quantized model outperforming the original is selling a rounding error. Second, and more important, the failure mode is honest and visible: the 2-bit file falls off a cliff on exactly the tasks that matter, 28.6% on DeepSWE and 86.0% on AIME. The method has a floor, the authors show you where it is, and they tell you not to use that file. That is rarer than it should be.

## The bill, and the catch

So what does this cost to actually run? The model card's own speed table, measured on a single RTX PRO 6000, puts the 3-bit file at 88.9 tokens per second at a 4K context, falling to 70.7 at 64K. That is slightly slower than Unsloth's UD-IQ3_XXS file of similar size on the same card, 94.7 and 74.8 tokens per second respectively. Smaller did not mean faster here. It meant the same speed, in a fifth of the memory, with the agent capability intact. On a 24 GB GPU the 3-bit file fits roughly a 135,000-token context; the model's full 262,144-token context needs about 30 GB of GPU memory, because the KV cache and activations are still stored in BF16. Long sessions still cost memory. They just cost much less of it in weights.

And there is a real catch, the kind that decides whether this is a download or a weekend project. The files only run on Nari Labs' own fork of llama.cpp, release b12431-nariv0. Stock llama.cpp, Ollama, and LM Studio cannot load the new tensor types yet. The fork is tuned for SM120 — the RTX PRO 6000 class of Blackwell card — while Ampere, Ada, and Hopper cards are slower than comparable GGUFs for now, GeForce cards have not been tested at all, and on an M3 Pro Mac with 18 GB of unified memory the 3-bit file decodes at about 3.8 tokens per second, which is a demonstration, not a workflow. The vision tower stays in BF16, the multi-token prediction module is not included yet, and the team says KV-cache quantization is next. It is a first release from a small team: strong where it counts, narrow where it doesn't, honest about both.

The Hacker News thread is small so far — the post, from the author himself, reached the front page at number 5 with 49 points and 9 comments in the early crawl, rising to 66 points and 12 comments by the evening check. That is not a verdict — a new paper from a team nobody had heard of a week ago, and the discussion has not caught up with the numbers yet. The numbers are on the model card, measured in the authors' own harness, with the failure case published alongside the success.

## What this changes for builders

For builders, the takeaway is practical: the binding constraint on running a capable coding agent locally has quietly moved. A year ago the question was whether a consumer GPU could hold the weights at all. The 53.8 GB full-precision file said no to most cards. The 10.1 GB file says yes to a 24 GB card, with a 135,000-token context, at roughly 89 tokens per second — and the agent inside it solves as many tasks as the original. The remaining constraint is the runtime: a fork, not the standard tools, on a card class most home users do not own yet. That is a software limitation with a merge path, not a physics limitation. The authors say they hope to merge support into upstream llama.cpp.

There is a larger pattern here, and it is the same one this column keeps returning to. The frontier labs keep building bigger models — this morning's was 750 billion parameters — and the open-weights world keeps finding ways to run the previous generation's capability on hardware people already own. The gap between what the model can do and what it costs to run it locally is closing from both ends. This week it closed by five times, in one file, from a team of one author.

That is the problem with measuring AI by parameter count. The meter never measured parameters. It measured what fits on your desk.
